Architecture & threat-model report

Keep the app out of the control plane.

Upgallery should declare gallery intent. A narrow, auditable reconciler should decide how that intent becomes nginx, TLS, and host filesystem state. In the common case, one wildcard route means there is nothing to provision per gallery at all.

Repository-specific Single-host Ansible Convex side effects GitHub Actions / GitOps 29 July 2026

The short answer

Use two lanes, not one universal provisioning path.

Platform-owned subdomains and arbitrary custom domains have different risk and operational requirements. Treating them identically creates unnecessary privileged automation.

1

Default lane: no per-gallery Ansible

Put all platform-owned galleries behind one stable Upgallery reverse proxy, wildcard DNS, and a wildcard certificate. Upgallery already selects the gallery from the original Host and path, so adding a gallery becomes a Convex metadata operation. The outer nginx config does not change.

2

Exception lane: GitOps PR for custom domains or host resources

Have an internal provisioning component create a narrowly scoped pull request containing typed desired state—not raw nginx or arbitrary Ansible variables. Validate it on a GitHub-hosted runner, require review, and deploy only after merge using one fixed playbook from the protected default branch.

3

Later: automate approval only after the contract is proven

If custom-domain volume makes manual review painful, keep the same desired-state format and replace the human gate with a policy broker or AWX job template. Do not respond by giving Upgallery SSH, Vault, or a generic “run any playbook” credential.

Most important answer to the permissions question A GitHub token is not naturally scoped to “only this playbook.” A token with Actions write permission can dispatch workflows in the repository; repository_dispatch is broader in a different way because it requires Contents write. The real restriction must live in the receiving workflow, repository boundary, branch protections, and runner/environment policy—not in an input named playbook.

Repository findings

The existing design already removes much of the provisioning problem.

These conclusions come from the current Upgallery and Yuzuyu source, not from a generic deployment pattern.

One application serves many hosts and paths

convex/galleries.ts stores one or more galleryHosts per gallery and resolves the longest matching root path. src/App.tsx passes the browser Host and path to that resolver.

The web container is already a shared frontend

deploy/nginx.conf.template serves one SPA, proxies /api/storage/, and exposes only the public media mounts. It deliberately preserves the original Host header.

Shared gallery roots are created lazily

The storage gateway derives a safe storage key and recursively creates its directory on upload. Shared image and protected uploader galleries therefore do not need a separate nginx webroot per gallery.

User-backed roots are the real host-side exception

User-backed galleries preserve normal filenames under a curated bind mount. They may need host ownership, group, mode, or an external mount before the container can write. That is a storage provisioning concern, not an outer nginx site root.

Site configuration is declarative and convergent

Yuzuyu loads every site YAML file, creates optional host roots, mounts them read-only into nginx, renders vhosts, removes stale generated vhosts, validates nginx, and reloads. This is already a good GitOps substrate.

Host convergence is already serialized

The reusable Actions workflow uses a single ansible-host concurrency group with cancel-in-progress: false. That is the right instinct for one mutable host and should be retained.

Trust boundary

Gallery input is data. Ansible is root-capable code execution.

Yuzuyu’s configured automation user escalates to root, while its Actions jobs receive the SSH private key and usually the Vault password. A single unsafe interpolation can therefore become host compromise.

Admin portal Authenticated but fallible user input
→
Desired-state boundary Schema, policy, idempotency, approval
→
Yuzuyu control plane SSH + sudo + Vault + Docker + nginx + TLS
The middle box is the security control. It must be impossible for the left-hand side to choose a command, playbook path, inventory, host, runner label, shell argument, Jinja expression, mount path, or raw nginx directive.

Required invariants

  1. The app submits a typed route/storage request, never executable text.
  2. The executable and inventory are fixed in trusted code on the protected branch.
  3. Hostnames, paths, IDs, and storage classes are revalidated at the control-plane boundary.
  4. Untrusted values are passed as structured data, never concatenated into shell commands.
  5. One convergence runs at a time; repeated requests are safe and idempotent.
  6. Plan/validation happens before credentials for production are released.
  7. Deletion of routes is separate from deletion of gallery bytes or host directories.
  8. Every request, review, run, revision, result, and retry is attributable.
Do not use the current generic site YAML as the app-facing API Today those files can express host_root, container_root, arbitrary locations, proxy_pass, and an extra map that becomes nginx directives. That flexibility is appropriate for trusted infrastructure authors, but much too powerful for application-generated input.

Detailed assessment

How each approach works—and where it fails.

A. One wildcard / shared Upgallery route

Provision Upgallery once. Give it a stable Docker network alias, route *.gallery.example.org to the web container, pass the original Host, and let Convex resolve the tenant.

Preferred default

Pros

  • No application-to-infrastructure credential.
  • Gallery creation is instant and transactional inside Convex.
  • No reload, race, certificate issuance, or config drift per gallery.
  • Smallest attack surface and operational burden.

Cons

  • Applies only to names under DNS zones you control.
  • Wildcard certificates require DNS-01 automation.
  • Does not by itself provision user-backed Unix directories or mounts.

Let’s Encrypt documents that DNS-01 can issue wildcard certificates and recommends an API-capable DNS provider for automated renewals: challenge types.

B. GitOps pull request

Upgallery records a provisioning request. A GitHub App or narrow broker writes one typed declaration on a new branch and opens a PR. CI validates the declaration and renders the expected diff. A CODEOWNER approves it; merge triggers the fixed deploy workflow.

Preferred custom domains

Pros

  • Excellent audit trail, preview, approval, and rollback via Git.
  • The app cannot directly reach the host or deployment secrets.
  • Branch protection and required checks provide independent gates.
  • Fits Yuzuyu’s existing declarative per-site model.

Cons

  • Not immediate while manual approval is required.
  • A Contents-write GitHub App can propose changes anywhere in its installed repo; GitHub permissions are not path-scoped.
  • Care is required so PR validation never receives production secrets or runs on a privileged self-hosted runner.
Protect main, require the provisioning validation check and a CODEOWNER review, dismiss stale approvals, require approval of the latest push, and disallow bypass. GitHub documents required reviews, status checks, and code-owner enforcement in branch protection.

C. Direct, fixed GitHub Actions dispatch

A Convex internal action calls the GitHub workflow-dispatch API with a gallery request ID. The trusted workflow fetches the canonical spec, validates it, and invokes one hard-coded Upgallery reconcile playbook.

Reasonable shortcut

Pros

  • Fast user experience and little extra infrastructure.
  • Actions run history, environment gates, and existing host concurrency remain available.
  • workflow_dispatch now returns run URLs/IDs, making status correlation straightforward.

Cons

  • Actions-write permission is not limited to one workflow.
  • External side effects are not atomic with gallery creation.
  • Passing the full gallery spec as dispatch inputs increases injection and replay risk.

Prefer workflow_dispatch over repository_dispatch here: the former requires Actions write, whereas the repository-dispatch endpoint requires Contents write. In either case, the receiver must use a fixed event/workflow and must not accept a playbook path. See GitHub’s workflow dispatch API and repository dispatch API.

D. Dedicated provisioning broker or pull reconciler

A small service owns the GitHub/SSH credential and exposes only domain-specific operations such as ensureUpgalleryRoute(requestId). It can poll Convex for pending desired state, so the application never calls inward.

Best mature design

Pros

  • Strongest application/control-plane separation.
  • Easy to enforce allowlists, schemas, idempotency, rate limits, and retries.
  • A pull model needs no public webhook ingress to the host.
  • Can support a fully automatic admin experience once policy is trusted.

Cons

  • Another service to deploy, monitor, patch, and back up.
  • You must design authentication and result reporting.
  • May be excessive until custom-domain volume justifies it.

A pull reconciler can use a service credential only to read pending requests and write results. It compares a spec hash with the applied revision, runs the fixed playbook only when they differ, and remains safe under duplicates or restarts.

E. AWX / Automation Controller

Import Yuzuyu as a project, define one job template with a fixed inventory, playbook, credential, and survey, then give a service account only the Execute role on that template.

Secure but heavyweight

Pros

  • Purpose-built job-template RBAC and credential isolation.
  • API, run history, approvals/workflows, surveys, and notifications.
  • Directly answers “only this playbook” more cleanly than GitHub tokens.

Cons

  • Substantial platform overhead for a single host and one narrow operation.
  • Requires its own upgrades, database, backups, and availability planning.
  • Survey/extra variables still require strict validation.

AWX’s RBAC includes an Execute role that runs assigned job templates, without granting template administration: AWX RBAC documentation.

F. Event-Driven Ansible webhook / rulebook

Run an Ansible Rulebook event source, authenticate Upgallery events with HMAC or a bearer token, match only a narrow event shape, and invoke a fixed playbook or Automation Controller job template.

Situational

Pros

  • Purpose-built event-to-automation mapping.
  • The webhook source supports bearer tokens, HMAC, TLS, and mTLS inputs.
  • Rules can explicitly map one event type to one fixed action.

Cons

  • Adds a long-running event service and usually an ingress endpoint.
  • Push webhooks need replay protection, deduplication, retry, and downtime handling.
  • Without Automation Controller, audit/history and RBAC are thinner than the GitOps or AWX options.

This is attractive if Event-Driven Ansible is already part of the infrastructure. It is not a shortcut around the desired-state boundary: accept a request ID, validate canonical data, and run a fixed action. Ansible’s own guidance notes that callback-style sources are sensitive to data loss when the receiver is unavailable. See Rulebook event sources.

G. Restricted SSH forced command or sudo wrapper

A dedicated key is restricted in authorized_keys to a fixed wrapper. The wrapper accepts a request ID or tightly validated hostname and runs exactly one local command.

Use only if GitHub is unwanted

Pros

  • Small and fast; no new automation platform.
  • Can be narrower than the existing general Ansible SSH key.
  • Works without GitHub Actions availability.

Cons

  • Custom security boundary that is easy to weaken with quoting, environment, or path mistakes.
  • Weak workflow history, approval, diff, and rollback story.
  • Places a host-reaching credential closer to the app.

If used, the key must have a forced command, no PTY, no forwarding, a source-address restriction where practical, and no general shell. The wrapper should accept an opaque request ID and retrieve canonical data, not accept arbitrary --extra-vars.

H. Give Upgallery Ansible, SSH, or Docker access

The app container receives Yuzuyu’s SSH key/Vault password, mounts the repo or Docker socket, or can construct an ansible-playbook command.

Do not do this
A compromised app, vulnerable dependency, stolen admin session, or input validation bug would become root-equivalent access to the host. Ansible tags are task-selection controls, not an authorization boundary. A playbook allowlist enforced by the caller is meaningless after the caller itself is compromised.

GitHub-specific answer

Runners can be restricted; tokens and workflows need separate controls.

Can a token run only one workflow?

Not as a per-workflow repository permission. The dispatch API requires Actions write. That permission also covers other workflow-management operations in the repository. Use a GitHub App with minimum repository access, but assume the token is repository-scoped—not workflow-scoped.

Can a runner accept only selected workflows?

Yes, organization/enterprise runner groups can be limited to selected repositories and selected workflow paths pinned to a branch, tag, or SHA. Only jobs directly defined in those workflows receive access. Availability depends on account/organization configuration.

Should this run on the Yuzuyu host?

Prefer the current GitHub-hosted runner + SSH model. A persistent runner on the managed host turns workflow code execution into local host execution and expands the blast radius. If a self-hosted runner is used, isolate it from the host and restrict its runner group to the exact deployment workflow.

Can an environment protect the SSH key?

Yes. Put deployment secrets in a production environment and reference that environment only from the deploy job. Protection rules can require reviewers and restrict branches before the job starts or receives secrets, subject to GitHub plan and repository visibility.

Recommended GitHub controls

  1. Add a dedicated deploy workflow with no playbook, inventory, limit, runner, or shell input. Hard-code the Upgallery reconcile playbook.
  2. Run untrusted PR validation on a GitHub-hosted runner with read-only GITHUB_TOKEN, no SSH/Vault secrets, and no production environment.
  3. Deploy only on a push to protected main, using a production environment and the existing global host concurrency group.
  4. Protect the workflow, provisioning schema, renderer, and CODEOWNERS file themselves with code ownership and no-bypass rules.
  5. Pin third-party actions to full commit SHAs. GitHub states this is the only immutable way to reference an action; Yuzuyu currently uses movable major-version tags for checkout and Python setup.
  6. Keep the verified KNOWN_HOSTS secret mandatory for automated production reconciliation; remove the current disable-checking fallback from this narrow workflow.
  7. Give the GitHub App only the repository permissions needed for its mode. GitHub Apps start with no permissions, and GitHub recommends selecting the minimum required permissions.
Self-hosted runner warning GitHub explicitly notes that self-hosted runners are not guaranteed to be clean or ephemeral and can be persistently compromised by untrusted workflow code. Environment approvals do not make the machine isolated. See Secure use reference and runner-group access controls.

Recommended target design

Declare, review, converge, report.

Keep the contract small enough that it can be fully validated and safely rendered without trusting application-supplied infrastructure syntax.

A deliberately narrow declaration

apiVersion: infrastructure.nyanya.org/v1
kind: UpgalleryRoute
metadata:
  requestId: "provisioning-request-id"
  galleryId: "convex-gallery-id"
spec:
  hostname: "photos.customer.example"
  pathPrefix: "/"
  tlsMode: "http01"
  storageClass: "shared"

The control plane—not the declaration—owns the upstream service name, container network, nginx template, filesystem base directories, certificate paths, SSH inventory, and playbook. Reject unknown fields. For platform-owned names, also enforce an allowed suffix. For custom domains, verify DNS ownership/readiness before certificate issuance.

Yuzuyu changes

  • Add an Upgallery service wrapper, container/network definitions, and stable aliases.
  • Add one wildcard vhost for platform subdomains.
  • Add a separate typed declaration directory for custom routes.
  • Build a renderer that rejects unknown fields and derives all nginx directives.
  • Add one reconcile_routes.yml playbook and a dedicated workflow.
  • Use a one-site certificate task or a safely filtered reconciliation, rather than exposing “certbot all” as an app-selected action.

Upgallery changes

  • Add a provisioning request/outbox table separate from gallery content state.
  • Track desired and applied spec hashes, attempt count, external run/PR URL, timestamps, and errors.
  • Schedule an internal action only after the gallery mutation commits.
  • Show provisioning, awaiting DNS, awaiting review, ready, and failed in admin.
  • Do not treat an unprovisioned host as a fully active OAuth return origin.
  • Make retry explicit and idempotent; never roll back content metadata because an external call timed out.

Suggested lifecycle

draft→ pending→ awaiting_dns→ awaiting_review→ deploying→ ready
failed_retryable↻ pending | retiring→ route_removed
Why an outbox is necessary Convex mutations are transactional, but actions that call external APIs have side effects and are not automatically retried. Scheduling an internal action from the creation mutation is atomically tied to the commit, but the external operation still needs an idempotency key, observed status, and explicit retry/reconciliation. Convex documents these guarantees in Scheduled Functions and Actions.

Failure semantics worth deciding up front

Duplicate event

Same request ID + same spec hash returns the existing PR/run/result. Same request ID + different spec is rejected.

DNS not ready

Remain in awaiting_dns; do not repeatedly hit ACME. Offer a recheck button and bounded background retry.

nginx test fails

Do not reload. Preserve current live config, mark the requested revision failed, and surface the sanitized validation error.

Run status is lost

Reconcile desired spec hash against the applied marker on the host or merged Git revision; never infer success from an HTTP timeout.

Gallery deleted

Remove routing after a grace period. Do not recursively remove storage roots or certificates in the same operation.

Two simultaneous edits

Last desired revision wins, but host convergence remains serialized and records exactly which revision became active.

Pragmatic rollout

Start with the design that is safest to change later.

Remove avoidable per-gallery work

Deploy Upgallery as one Yuzuyu-managed service. Add one stable outer proxy and platform-owned wildcard DNS/TLS. Make this the default gallery hostname mode in admin.

Define the narrow desired-state schema

Separate route requests from general Yuzuyu nginx site YAML. Add strict schema validation, hostname/path normalization, allowed storage classes, spec hashing, and render-only tests.

Add PR-based custom-domain onboarding

Create provisioning branches/PRs with a GitHub App, validate without secrets on GitHub-hosted runners, and require a protected merge. Keep Upgallery’s admin state asynchronous and link to the PR.

Deploy from protected main only

Use a dedicated workflow, production environment, explicit secrets, mandatory host-key verification, pinned actions, and the existing global single-host concurrency group.

Automate policy, not authority

Once the request schema and failure modes are stable, auto-approve low-risk cases such as verified custom domains at /. Continue requiring review for shared-host path edits, user mounts, and all destructive operations.

One Yuzuyu-specific hardening item before automation The current reusable workflow inherits repository secrets and can disable SSH host-key checking when KNOWN_HOSTS is missing. That escape hatch may be useful for manual bootstrap, but the automated Upgallery reconciliation workflow should fail closed instead.
